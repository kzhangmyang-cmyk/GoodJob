# AI 获客智能体真实闭环收口设计

日期：2026-07-26

状态：基于现有已批准架构的增量设计

基线：GoodJob 1.09，分支 `feature/ai-acquisition-agent-design`

## 1. 目标

不重写现有 Pi、模型网关、搜索 Provider、计划审批、候选证据、评分、
作战卡、审核和 CRM 领域能力，只补齐真实运行链路中的三个断点：

1. 真实获客运行结果能够被 AI 增长参谋持续读取和展示；
2. 搜索完成后自动执行研究、评分、财务评估和优先级排序；
3. 高优先级候选自动生成可打开的客户作战卡。

最终用户体验固定为：

```text
用户描述获客目标
→ AI 生成结构化计划
→ 人工确认计划
→ 自动搜索、去重、研究、评分、财务评估、生成作战卡
→ AI 汇报优先客户和判断依据
→ 人工确认转入 CRM 或创建触达审核任务
```

前台只展示一个“AI 增长参谋”。搜索规划、客户研究、资格评分、财务价值、
作战卡等是后台专业能力，不让客户在多个智能体之间手工切换。

## 2. 方案比较与选择

### 方案一：让 Pi 自由决定全部执行步骤

优点是形式上最像自主智能体。缺点是不可预测，容易重复搜索、超预算、遗漏
评分步骤，并削弱现有队列、幂等、审批和审计能力。不采用。

### 方案二：每一步都由用户点击确认

优点是控制最强。缺点是搜索结束后还要逐条点击研究、评分和生成作战卡，
用户会感觉 AI 只会提供按钮，不会主动完成任务。不采用。

### 方案三：Pi 总控入口 + 确定性自动流水线 + 两道人工作业门

Pi 负责理解目标、生成计划、解释结果和接受追问；GoodJob Worker 负责按固定
状态机执行搜索后的全部处理。只在执行计划前和 CRM/触达前要求人工确认。

该方案复用现有架构，运行可恢复、可审计、可控成本，是本次选定方案。

## 3. 自动处理流水线

每个获客 Run 在搜索分片进入终态后，启动候选处理流水线：

```text
source_ingested
→ identity_resolution
→ deterministic_gate
→ research
→ qualification
→ financial_value
→ battle_card
→ priority_ranked
```

### 3.1 身份与硬门禁

- 先复用现有企业域名、统一社会信用代码和公开主页身份规则；
- 身份不足的候选标记为 `needs_research`，不得伪装成已核实客户；
- 明确拒绝、勿扰、非公开数据、证据过期或来源缺失的候选停止自动晋级；
- 同一强身份合并为同一个候选，保留全部来源证据。

### 3.2 研究

研究阶段只能读取公开、允许访问的来源。它先使用已有搜索证据，再针对缺失项
生成受限补充查询：

- 企业概况与主营业务；
- 近期招聘、扩张、采购、招标、融资或经营变化；
- 疑似现有供应商及其证据；
- 可能参与采购的部门和商务角色；
- 与目标产品相关的明确需求和负向信号。

补充研究有独立的查询数、页面数、时间和费用上限。来源受限或没有证据时输出
“未知”，不能由模型猜测补齐。

### 3.3 评分与财务价值

所有通过硬门禁的候选先执行确定性规则评分，再由模型结合证据生成解释性判断。

意向判断至少包含：

- ICP 匹配；
- 需求明确度；
- 购买阶段；
- 近期业务信号；
- 决策角色可达性；
- 负向信号和证据质量。

财务价值至少包含：

- 预计成交区间；
- 成交概率；
- 预计毛利区间；
- 销售周期；
- 回款周期；
- 服务复杂度和账期风险。

模型输出不能覆盖硬门禁。所有金额使用最小货币单位，概率使用基点，并保存
规则版本、模型快照、证据引用和置信度。

### 3.4 作战卡

对通过全部硬门禁且资格等级为 S/A（或综合分不低于 70）的候选自动生成作战卡。
新结果使用版本化的 `battle-card.v2` 契约；已有 `battle-card.v1` 继续只读兼容，
不在迁移时伪造缺失字段。V2 作战卡固定包含：

- 客户概况；
- 需求判断与证据链；
- 供应商假设；
- 采购决策链；
- 采购偏好和商务沟通方式；
- 推荐连接路径；
- 分角色、分渠道开场草稿；
- 不建议动作；
- 财务价值摘要。

每项内容必须标记为事实、推测或未知，并引用证据和置信度。作战卡生成失败不
影响其他候选完成，候选进入可重试状态。

## 4. 运行展示契约

补充现有前端已经调用、后端尚未实现的只读接口：

```text
GET /api/v1/acquisition/runs/:id/presentation?after=<cursor>&limit=<n>
```

响应返回：

- Run 状态和汇总指标；
- 搜索查询及 Provider 执行状态；
- 分片进度和部分失败；
- 新增、合并、待研究、已评分和已生成作战卡的候选事件；
- 当前优先客户；
- 可继续读取的增量游标。

接口只聚合权威状态，不创建候选、不触发模型调用、不伪造计时进度。前端真实
模式只能依据该接口展示进展；演示模式必须明确标记为演示回放。

## 5. 编排与并发

- 每个候选的每个阶段使用稳定幂等键；
- 同一候选同一版本最多存在一个活动处理任务；
- 新证据使旧资格判断、财务评估和作战卡失效并进入重新评估；
- 单个候选失败不终止整个 Run；
- Run 暂停或取消必须传播到候选处理任务；
- 同一 AI 增长参谋会话同一时间只运行一个活动任务；
- Pi 单次运行限制工具调用轮数、总时间、模型费用和外部搜索费用。

## 6. 错误与恢复

系统明确区分：

- `partial_success`：部分来源或候选失败，已有结果仍可使用；
- `needs_research`：身份或证据不足，等待补充研究；
- `budget_exhausted`：达到时间、调用量或费用上限；
- `connection_required`：客户未配置可用模型或搜索连接；
- `model_output_invalid`：结构化输出修复后仍不合法；
- `access_restricted`：来源要求登录、验证码或拒绝访问。

失败任务保存稳定错误码和可重试阶段。重试沿用原 Run、模型、Prompt、Schema
和连接快照，不静默切换 Provider。

## 7. 前端结果顺序

完成页按老板的决策顺序展示：

1. 本次发现多少有效商机；
2. 最值得跟进的三至五个客户；
3. 推荐原因和关键证据；
4. 今天建议执行的动作；
5. 候选列表与客户作战卡；
6. 可展开的搜索查询、数据源和技术执行日志。

候选卡点击后直接打开已经存在的作战卡；如果卡片仍在生成，展示真实任务状态，
完成后自动刷新，不要求用户重新点击生成。

## 8. 验收标准

1. 真实 Run 可从计划审批一直执行到优先客户和作战卡，不需要中途人工点击；
2. 前端能通过增量展示接口看见真实查询、Provider、进度、候选和部分失败；
3. 搜索完成后，符合门禁的候选自动产生资格判断和财务价值；
4. 达到阈值的候选自动产生带证据的结构化作战卡；
5. 页面能打开真实和演示作战卡，演示数据不会冒充真实运行；
6. 暂停、恢复、取消、重试、幂等和预算上限均有自动测试；
7. 任何身份、供应商、决策角色和采购偏好都不能在没有证据时显示为事实；
8. CRM 转换和触达仍必须经过人工确认。

## 9. 分工边界

为了方便两人用 Codex 并行开发：

- 智能体与财务决策分支负责流水线编排、研究、评分、财务价值、作战卡契约及
  后端展示投影；
- 前后端工程分支负责页面 ViewModel、运行进度、结果排序、抽屉交互和 CRM
  页面衔接；
- 双方只通过版本化 OpenAPI/JSON Schema 对接，不直接修改对方内部状态结构。
