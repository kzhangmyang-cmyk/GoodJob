## Problem Statement

中国市场上的许多“AI 获客”产品，本质仍是关键词脚本、批量采集和机械触达。它们能够增加动作数量，却难以回答以下真正影响成交的问题：

1. 哪些公开互动和需求信号构成真实商机；
2. 同一个用户在多个内容和时间窗口中的行为是否应合并判断；
3. 哪个客户既有意向，又有足够的财务价值；
4. 应该找哪个角色、从什么需求切入、使用哪种沟通策略；
5. 哪些动作可以在客户预授权和平台实际能力范围内自动完成；
6. 哪些异常、敏感、低置信度或高风险场景必须由人工接管；
7. 从发现、互动、进入私域、成交到回款，是否能够完整归因并持续优化。

现有 GoodJob 1.09 已具备通用公开搜索、证据留存、主体归一、资格评分、财务价值、客户作战卡、审核、CRM 转换和结果反馈能力，但尚未具备抖音平台连接器、平台事件模型、多信号聚合和受控自动动作执行能力。新的营销前端已经形成清晰的获客任务、平台卡片和执行时间线视觉，但仍主要是静态演示数据，尚未与 GoodJob 的真实领域模型连接。

因此，本项目需要把“通用 AI 获客内核”扩展为可按平台安装能力包的增长系统，并以抖音作为第一个落地平台：让客户能用自然语言配置目标，系统持续发现公开或已授权商机，用 AI 进行多信号判断和个性化策略生成，在预授权范围内自动执行允许的动作，遇到例外自动转人工，并把结果连接到 CRM、财务价值和渠道 ROI。

## Solution

产品采用“一个 AI 增长参谋 + 多个纯函数 Skill + 确定性工作流 + 平台连接器 + 规则引擎”的架构，而不是堆叠多个相互自由对话的 Agent。

### 1. 用户可见产品形态

用户只面对一个“AI 增长参谋”。它负责：

- 理解行业、地区、产品、目标客户和经营目标；
- 生成可解释的抖音获客计划；
- 汇报任务进度、优先客户、推荐原因和下一步动作；
- 接受老板、销售、运营和财务角色的自然语言追问；
- 将用户确认转化为计划、规则、预算或任务，而不是仅返回聊天文字。

后台专业能力以 Skill 和工作流存在，包括 ICP、搜索规划、信号标准化、身份合并、意向评分、财务价值、客户研究、作战卡、连接策略、报价保护、对话跟进、动作策略和结果学习。

### 2. 抖音首发获客闭环

```text
自然语言经营目标
→ AI 生成抖音获客计划
→ 用户确认数据源、预算与自动动作边界
→ 公开搜索 / 用户链接 / 已授权抖音连接器发现信号
→ 平台事件标准化、去重与时间窗聚合
→ 主体身份解析与多信号资格评分
→ 财务价值、客户研究与客户作战卡
→ 连接策略与动作意图
→ 规则引擎判定自动执行 / 人工审核 / 禁止
→ 官方连接器执行允许动作并保存回执
→ 回复、拒绝、进入私域、成交、回款
→ CRM、渠道 ROI 与模型效果复盘
```

### 3. 三类数据入口

1. **公开搜索发现**：通过客户配置的官方搜索 API，检索公开可访问的抖音页面、账号、视频、话题和相关网页。
2. **用户提供内容**：用户提交公开抖音链接、Excel/CSV 或经过授权导出的业务数据。
3. **抖音官方授权连接器**：通过客户自己的抖音开放平台应用和账号授权，按实时能力快照接入已获批准的数据、事件和动作能力。

界面必须清晰展示每条数据的来源方式、授权状态、更新时间和可执行能力，不能把公开搜索描述为“扫描整个抖音”，也不能把未获授权的能力展示为已连接。

### 4. AI 的真实价值

AI 不只生成文案，而是承担以下语义决策：

- 将用户自然语言经营目标转为结构化 ICP 与获客计划；
- 从评论、账号主页、内容主题、重复互动、明确询价、业务痛点和负向信号中提取商机信号；
- 将单点行为放入时间窗口和主体上下文中综合判断；
- 输出 S/A/B/C/D 意向等级、财务价值、证据、置信度和反证；
- 推测现有供应商、决策链、采购偏好和商务沟通风格，并严格区分事实、推测和未知；
- 针对公开回复、已授权私信、电话、企微、邮件、表单等渠道生成不同策略；
- 分析对话阶段、异议和下一步动作；
- 用成交、回款、拒绝和流失结果反向评估信号、提示词和策略版本。

### 5. 自动化边界

“全自动”定义为：在客户预先确认的计划、预算、频率、内容策略和平台实际授权能力范围内，系统可持续自动发现、研究、评分、生成作战卡、排队并执行允许的动作；不要求用户逐条点击。

每个动作必须同时满足：

1. 当前平台连接器声明该能力可用；
2. 授权仍有效且作用域匹配；
3. 当前获客计划明确预授权该动作；
4. 客户不在勿扰名单且没有明确拒绝；
5. 频率、预算、内容、敏感词和重复度规则通过；
6. 动作幂等键尚未产生成功回执；
7. Skill 结论和规则版本可审计。

任一条件不满足时，系统只能进入 `review_required` 或 `blocked`，不能通过模拟点击、逆向协议、验证码规避或“模拟真人频率”补齐缺失能力。

### 6. 跨行业能力

系统不绑定单一垂直行业。行业差异通过租户级配置和知识库表达：

- 产品与服务资料；
- ICP、排除画像和需求信号；
- 成交案例、常见异议和禁用承诺；
- 价格、成本、毛利、回款和折扣规则；
- 角色、采购链和渠道策略；
- 行业词库与评估样本。

平台连接器、证据、工作流、审核、CRM 和财务模型保持通用。

## User Stories

### 获客计划与配置

1. 作为老板，我希望用一句话描述产品、行业、地区和目标客户，让 AI 生成可执行的抖音获客计划。
2. 作为运营，我希望查看并修改 AI 生成的关键词、需求信号、排除条件、数据来源和预算。
3. 作为管理员，我希望为每个计划选择公开搜索、用户链接、授权连接器或它们的组合。
4. 作为管理员，我希望在执行前看到抖音连接器的真实授权范围、到期时间和可用能力。
5. 作为老板，我希望预先决定哪些动作允许自动执行，哪些动作必须审核，哪些动作永久禁止。
6. 作为财务负责人，我希望为计划设置请求量、结果量、模型费用、搜索费用和总时长上限。
7. 作为团队成员，我希望计划审批后固化模型、提示词、规则、连接器和预算快照，避免执行时静默变化。

### 商机发现与证据

8. 作为运营，我希望系统通过公开搜索发现与目标行业、地区和需求相关的抖音页面及账号。
9. 作为运营，我希望手动提交抖音公开链接，并让系统沿用同一套清洗、去重和评分流程。
10. 作为管理员，我希望在获得官方授权后同步允许的数据和事件，并支持游标续传和断点恢复。
11. 作为销售，我希望每条候选都展示原始来源、时间、证据摘要和访问状态。
12. 作为销售，我希望同一账号在多个视频、评论和时间点的行为合并成一个候选，而不是重复客户。
13. 作为销售，我希望一句“多少钱”不会自动成为高意向，系统必须结合账号匹配、重复互动、业务场景和负向信号。
14. 作为审核员，我希望身份不明确的候选停留在待研究状态，而不是被 AI 猜成真实客户。

### AI 评分、研究与作战卡

15. 作为销售，我希望系统给每条候选输出 S/A/B/C/D 等级、分数、证据、反证、置信度和推荐动作。
16. 作为老板，我希望系统同时判断客户是否想买和是否值得做，优先展示高意向、高毛利、快回款客户。
17. 作为销售，我希望系统研究客户企业、近期动态、需求、疑似供应商和替代或补位机会。
18. 作为销售，我希望系统识别可能的需求发起人、影响者、采购、技术和最终决策人。
19. 作为销售，我希望系统根据公开商务证据和历史沟通推测采购偏好与沟通风格，并明确标注置信度。
20. 作为销售，我希望系统为高优先级客户自动生成客户作战卡，无需逐条点击。
21. 作为销售，我希望针对老板、运营、采购、技术和一线使用者得到不同开场策略。
22. 作为销售，我希望作战卡同时列出不建议动作，防止直接报价、过度承诺或无依据断言。

### 自动动作与人工接管

23. 作为管理员，我希望为每种动作设置 `auto_allowed`、`review_required` 或 `blocked` 策略。
24. 作为运营，我希望系统在允许范围内自动生成并执行公开回复任务，并保存平台回执。
25. 作为销售，我希望只有在官方能力、用户授权和消息额度均满足时，系统才创建已授权私信动作。
26. 作为审核员，我希望低置信度、敏感内容、频率超限、客户拒绝或连接器异常自动进入人工队列。
27. 作为审核员，我希望能看到动作目标、来源证据、候选等级、生成内容、策略判定和风险原因后再批准。
28. 作为管理员，我希望同一业务动作因重试、刷新或回调重复而最多成功执行一次。
29. 作为销售，我希望客户回复后系统自动更新对话阶段、意向分和下一步建议。
30. 作为客户，我希望明确拒绝后系统立即停止后续动作并写入勿扰状态。
31. 作为管理员，我希望能够随时暂停计划、撤销自动动作授权并停止待执行任务。

### CRM、财务和经营决策

32. 作为销售，我希望达到转换条件的客户进入 CRM，并保留来源、证据、评分、作战卡和动作历史。
33. 作为销售主管，我希望看到每条线索从发现、回复、进入私域、报价、成交到回款的完整阶段。
34. 作为老板，我希望看到抖音渠道的线索数、高意向率、回复率、私域转化率、成交额、毛利和回款。
35. 作为财务负责人，我希望估算每条线索的成交区间、毛利、服务复杂度、销售周期和账期风险。
36. 作为老板，我希望按计划、账号、视频、内容、动作策略和模型版本进行 ROI 归因。
37. 作为老板，我希望 AI 每天给出优先客户、风险客户、预计成交和建议预算，而不是让我阅读所有表格。
38. 作为产品负责人，我希望真实成交、回款、拒绝和流失结果进入效果评估集，判断哪类信号和策略真正有效。

### 前端体验与协作

39. 作为客户，我希望进入产品第一屏就看到 AI 增长参谋、今日发现、自动任务、待接管和转化结果。
40. 作为客户，我希望平台卡片明确区分演示、公开搜索、用户导入和官方授权连接状态。
41. 作为客户，我希望任务时间线展示真实 Plan、Run、Shard、候选处理和动作执行状态。
42. 作为客户，我希望点击候选即可打开真实证据、评分、财务价值和作战卡。
43. 作为客户，我希望错误状态可解释，包括连接未配置、授权到期、额度不足、部分成功和能力暂不可用。
44. 作为开发协作者，我希望前后端只通过版本化 OpenAPI、JSON Schema 和 ViewModel 契约协作，减少分支合并冲突。
45. 作为产品负责人，我希望跨行业差异通过配置、样本和知识库迭代，不通过复制一套行业专用后端实现。

## Implementation Decisions

### 1. 复用现有 GoodJob 领域内核

继续使用现有 Plan、Run、Shard、Candidate、Evidence、Qualification、Financial Value、Battle Card、Review、CRM Conversion 和 Outcome Feedback。不得为抖音另建一套平行的候选、评分或 CRM 数据模型。

### 2. 新增平台连接器边界

搜索 Provider 与内容来源平台必须分离：

- `SearchProvider` 表示百度、腾讯、Tavily 等“如何发现网页”；
- `PlatformConnector` 表示抖音等“如何授权读取平台数据或执行动作”；
- `sourcePlatform` 表示证据内容实际来自哪个平台。

连接器至少保存租户、账号、授权范围、能力快照、凭据版本、Webhook/Poll 模式、同步游标、状态、到期时间和限额。

### 3. 新增平台事件证据与信号聚合

平台数据先标准化为不可变事件证据，再在时间窗口内聚合为候选信号。事件至少包含平台、账号、视频、评论/消息/表单、平台事件 ID、主体标识、原文哈希、发生与捕获时间、授权快照、去重键和访问状态。

资格评分读取聚合信号，不直接把单条评论当作客户结论。新事件到达后，按候选和决策版本幂等触发重评。

### 4. Agent、Skill、工作流和规则严格分层

- **AI 增长参谋 / Pi**：理解目标、选择已注册 Skill、解释结果，不直接持有平台凭据或执行外部动作。
- **Skill**：接受版本化输入，返回结构化建议和证据引用；无数据库写入、无网络副作用、无消息发送。
- **确定性工作流**：负责任务顺序、队列、预算、限流、重试、暂停、恢复、幂等和状态机。
- **规则引擎**：对动作输出自动、审核或禁止结论；硬规则优先于模型建议。
- **平台连接器 Worker**：唯一可以读取平台凭据并执行官方动作的组件，成功或失败均生成回执。

### 5. 自动动作领域模型

新增 `ActionPolicy`、`PlatformActionIntent`、`ActionDecision`、`ActionJob` 和 `ActionReceipt`。动作意图不能直接执行；规则引擎必须基于能力、授权、计划快照、勿扰、频率、预算、内容和幂等状态生成决定。

第一阶段的动作类型由抖音连接器实时能力探测决定。代码不得假定所有账号均支持评论回复、主动私信、群消息或其他动作。

### 6. 前端采用聚合投影，不复制领域写逻辑

将新营销前端的“获客任务”映射为 `AcquisitionPlan + latest AcquisitionRun`，增加只读首页和任务聚合投影；所有创建、审批、运行、审核和转换继续调用 GoodJob 的权威接口。

前端保留现有视觉语言，但逐步拆出结构化组件和 API 状态层，不继续扩展硬编码 DOM 演示数据。

### 7. 契约真源先收口

在平台开发前，统一实际运行时 OpenAPI 与仓库中的契约 YAML，明确唯一真源。所有新接口必须同时提供 JSON Schema、OpenAPI、错误码、幂等和并发语义。

### 8. BYOK 与租户隔离

客户继续填写自己的官方模型、搜索和平台应用凭据。凭据服务端加密、只返回掩码，运行绑定凭据版本和能力快照。团队、租户和账号数据严格隔离。

### 9. 开源项目使用原则

相关开源仓库只放入独立参考源码区，并写入来源、commit、许可证和用途清单。允许的复用方式取决于许可证；GPL 或无许可证仓库只做架构研究，禁止把代码复制到闭源生产仓库。所有引入生产依赖均需单独决策记录和安全审计。

## Testing Decisions

### 1. 契约接缝

- JSON Schema 校验所有 Skill 输入输出、平台事件、动作策略和回执；
- OpenAPI 覆盖真实运行路径、错误码、ETag、`If-Match` 和 `Idempotency-Key`；
- 增加契约漂移检查，禁止运行时代码和静态 YAML 再次分叉。

### 2. 领域闭环接缝

覆盖：

```text
Plan → Run → Platform/Search Evidence → Signal Aggregate
→ Candidate → Qualification → Financial Value → Battle Card
→ Action Decision → Action Receipt → CRM → Outcome
```

验证版本失效、重新评分、部分失败、暂停恢复、预算耗尽、明确拒绝和勿扰门禁。

### 3. 平台适配器接缝

使用本地 Fixture 和模拟官方服务覆盖：

- OAuth、授权到期和能力快照变化；
- Webhook 签名、重放、乱序、重复和无效事件；
- 游标同步、429、退避、超时和断点续跑；
- 平台稳定身份、事件去重和来源平台识别；
- 自动、审核、禁止三类策略；
- 动作只执行一次并保存真实回执。

自动测试默认不访问真实抖音网络。

### 4. Skill 黄金样本

建立跨行业中文样本集，至少覆盖：

- 单句弱信号；
- 多次互动叠加强信号；
- 明确询价但行业不匹配；
- 同行、广告、拒绝和投诉；
- 高意向低财务价值；
- 低意向高潜在价值；
- 无证据的供应商和性格推测；
- 报价、异议和跟进阶段变化。

每个版本记录精确率、召回率、越权动作率、无证据断言率、人工改判率和成本。

### 5. 前端状态机接缝

覆盖 idle、planning、awaiting approval、running、partial success、paused、connection required、capability unavailable、review required、completed 和 failed。真实模式不允许回退为假进度或演示数字。

### 6. 端到端发布接缝

在现有获客 E2E 基础上增加从抖音事件 Fixture 到候选、评分、作战卡、动作决策、回执、CRM 和 Outcome 的完整路径；任何未声明的外部调用失败测试。

## Out of Scope

首个抖音发布里不包含：

- 快手、小红书、微博、微信公众号的真实连接器；
- 非官方协议、客户端 Hook、逆向接口、验证码绕过或设备农场；
- 模拟真人频率以规避平台检测；
- 采集非公开聊天、通讯录、私人朋友圈、家庭住址、轨迹、健康、宗教、金融账户等敏感或私密信息；
- 在没有平台能力和用户授权时主动联系陌生人；
- 用模型推测代替身份、供应商、采购需求或动作回执事实；
- 保证不封号、保证成交、保证 ROI 或保证回款；
- 第一阶段重做完整 CRM、ERP、财务会计系统或企业级 EPM；
- 3D 数字人、语音克隆或只增加视觉噱头的“贾维斯”动画。

## Further Notes

### 发布阶段

1. **阶段 A：真实展示闭环**  
   统一契约，接入新前端，完成公开搜索和用户链接的抖音商机发现、评分、作战卡与 CRM 闭环。

2. **阶段 B：授权数据闭环**  
   接入抖音官方 OAuth、能力探测、授权数据/事件同步、游标和 Webhook。

3. **阶段 C：受控自动转化**  
   上线动作策略、任务队列、官方动作执行、回执、人工例外接管和撤销授权。

4. **阶段 D：经营学习闭环**  
   完成对话跟进、渠道 ROI、成交回款归因和版本化效果评估。

### 成功指标

- 有效候选率；
- S/A 级线索准确率；
- 无证据断言率；
- 自动动作成功率和重复执行率；
- 人工接管率与人工改判率；
- 回复、进入私域、报价、成交和回款转化率；
- 每条有效线索成本和每个成交客户获客成本；
- 渠道毛利 ROI 与回款周期；
- 客户撤销授权、拒绝和投诉率。

### 后续平台扩展

抖音能力完成后，快手、小红书、微博和微信公众号必须复用相同的 Connector、Event Evidence、Signal Aggregate、Action Policy、Receipt 和 Outcome 契约，只新增平台适配器与平台专属 Skill，不复制领域内核。
